MotoLog / Ride Tracker
Full Technical Audit Report

Project: MotoLog motorcycle ride tracker

Repository: /home/abrar/Documents/Websites/ride_tracker

Audit scope: Android application, Kotlin Multiplatform shared module, persistence, tracking service, GPX/CSV/backup flows, permissions, build configuration, tests and generated lint reports.

Audit status: Read-only audit. No source files were modified.

Executive summary

The project has a solid architecture, a substantial shared-domain test suite, good separation between Android and shared logic, and successful debug/release builds. The GPS calculation engine is thoughtfully designed and tested.

The main weakness is that the most failure-sensitive code is outside the tested pure-domain layer: foreground-service lifecycle, persistence batching, backup restoration, import validation and Android process death. Those areas currently permit data loss, privacy-policy violations or inconsistent state under realistic conditions.

Most urgent issues:
  1. Device-transfer backup rules can transfer the entire application root, potentially including GPS databases.
  2. Starting and stopping a ride can race before activeRideId has been assigned.
  3. Restore can delete existing user data before proving that the backup is complete and valid.
  4. Unlimited point buffering can grow without bound if Room writes fail or stall.
  5. Service destruction does not flush pending points or finalize an active ride.
  6. GPX import accepts invalid coordinates and can create corrupt rides.

Validation performed

  • Inspected Android manifest, backup rules, Gradle configuration, module structure and source/test inventory.
  • Inspected tracking, GPS filtering, persistence, backup, GPX import/export and recovery paths.
  • Ran the existing unit-test task successfully.
  • Built the release APK successfully.
  • Reviewed generated Android lint findings and warnings.

Passing tests and a successful release build do not prove correct behavior under process death, storage failure, malformed imports, backup corruption or real GPS callback behavior.

1. Privacy leak through device-transfer backup

Location: app/src/main/res/xml/data_extraction_rules.xml:7-10

<device-transfer>
    <include domain="root" path="." />
</device-transfer>

The database is excluded from cloud backup, but the entire application root is explicitly included for device transfer. Depending on Android's device-transfer implementation, this can transfer Room database files, GPS points, ride history, preferences and temporary files.

This conflicts with the documented privacy claim that location data remains on-device.

Recommended fix: Use a narrow allowlist. Exclude the database from both cloud backup and device transfer, or explicitly document that device migration transfers ride data. Verify behavior on API 31+ devices.

2. Start/stop race can use an invalid ride ID

Location: app/src/main/java/com/abrar/motolog/service/TrackingService.kt:138-222, 500-526

handleStart() sets isTracking before launching asynchronous initialization. The database ride is inserted later. A stop command can arrive while activeRideId is still 0L.

Possible outcomes include stopping a nonexistent ride, leaving an active ride behind, starting GPS collection after stop, or writing inconsistent final metadata.

Recommended fix: Add explicit Idle/Starting/Tracking/Stopping states, store and cancel the startup job, validate activeRideId > 0, check state after suspension points, and serialize service commands through a mutex or actor.

3. Restore can wipe data from an incomplete archive

Location: app/src/main/java/com/abrar/motolog/data/io/BackupManager.kt:198-247, 248-267

The restore parser treats every archive entry except the manifest as optional. It then deletes all current tables before inserting whichever entries were found. An archive containing only a manifest can therefore clear existing data and restore nothing.

The manifest counts are parsed but not compared against the actual arrays. Foreign keys, duplicate IDs, timestamps, coordinates and enum values are also not fully validated before deletion.

Recommended fix: Require every expected entry, validate format version and manifest counts, validate relationships and values, stage the import in a temporary database or transaction, and only replace current data after validation succeeds.

4. Unlimited point buffering can cause memory growth

Location: TrackingService.kt:96-97, 593-607

private val pointChannel = Channel<RidePointEntity>(Channel.UNLIMITED)

If the Room batch writer fails, the location collector continues enqueueing points. Because the channel is unlimited, a long ride can grow the heap until the process is killed.

Recommended fix: Use a bounded channel, define backpressure behavior, retry database writes with backoff, expose persistence failure to the UI/notification, and stop safely if the data cannot be persisted.

5. Service destruction loses pending tracking data

Location: TrackingService.kt:775-791

onDestroy() cancels the service scope but does not drain the point channel, await the batch writer, checkpoint final stats or mark the ride as interrupted/recoverable.

Recommended fix: Stop callbacks first, drain and persist the queue, checkpoint the ride, mark it recoverable, then cancel jobs. Since Android may kill a process without calling onDestroy(), persist frequently enough to keep the loss window bounded.

6. START_NOT_STICKY conflicts with documented recovery

Location: TrackingService.kt:122-132

The service returns START_NOT_STICKY, so Android will not recreate it after process termination. This does not provide continuous tracking recovery; at most, the UI may later discover an incomplete ride.

Recommended fix: Decide whether the desired behavior is recover-later or resume-after-process-death. Use the appropriate restart mode, persist safe state, and avoid silently resuming location tracking without valid permission and user intent.

7. GPS loss detection is reset by poor-quality fixes

Location: TrackingService.kt:237-258, 395-410

lastLocationPointTime is updated before accuracy validation. A stream of inaccurate callbacks therefore prevents the signal-loss timeout from firing. The GPS-lost flag is also cleared before the fix is accepted.

Recommended fix: Track callback time and last-valid-fix time separately. Clear GPS-lost only after a fix passes validation and is accepted by the calculation engine.

8. GPX import accepts invalid coordinates

Location: GpxImporter.kt:105-106, 145-157

The parser checks only whether latitude and longitude parse as doubles. It does not enforce finite values or legal geographic ranges.

Recommended fix: Require finite latitude in [-90, 90] and longitude in [-180, 180]. Add tests for NaN, infinity, missing coordinates and out-of-range values. Reuse a common validator for live GPS, GPX import and backup restore.

9. GPX parser silently degrades XML security

Location: GpxImporter.kt:41-45

Security feature configuration failures are silently ignored. If a parser does not support a requested feature, parsing continues without proving that XXE/entity protections are active.

Recommended fix: Enable secure processing, restrict external access, reject DOCTYPE declarations, treat mandatory feature failures as parse failures, and add XXE/entity-expansion regression tests.

10. GPX import is not transactional

Location: SettingsViewModel.kt:349-403

Multiple tracks are saved one at a time. If a later track fails, earlier tracks remain saved and the user receives only a generic failure message.

Recommended fix: Validate all tracks first, then insert the entire import inside a repository-level Room transaction. Roll back the complete import on failure.

11. ZIP limits are applied after unrestricted reads

Location: BackupManager.kt:211-227 and inspectBackup():166-184

ZIP metadata sizes can be unknown. The code calls readBytes() before reliably enforcing decompressed-size limits. inspectBackup() has no size limit at all.

Recommended fix: Read entries through a bounded stream, abort during reading when the entry or total archive limit is exceeded, reject duplicate/unexpected entries, and enforce a maximum entry count.

12. Backup creation is not a consistent snapshot

Location: BackupManager.kt:100-104

Each table is read sequentially. If a ride is active, the manifest, rides and points can represent different moments and may not correspond to one coherent database state.

Recommended fix: Read all tables in a Room transaction or prohibit backups during active recording. Define and test snapshot semantics.

13. Restore settings are outside database atomicity

Location: BackupManager.kt:269-290

Database restoration is transactional only when a database instance is available. Settings are applied afterward and invalid enum values are silently ignored.

Recommended fix: Validate all settings before modifying anything, return explicit errors, and add a restore journal or rollback strategy for the unavoidable Room/DataStore boundary.

Medium-priority correctness findings

14. Live and persisted timestamps use different clocks

Location: TrackingService.kt:264-275, 310-319

The calculator uses elapsed realtime where available, while persisted points use wall-clock epoch time. Recovery replays wall-clock timestamps. Clock changes can therefore produce different gap detection, elapsed time, speed and auto-pause behavior after recovery.

Recommendation: Persist both epoch time for display/export and monotonic elapsed time for calculations and recovery.

15. Silent exception swallowing hides data-integrity failures

Broad or silent catches occur in tracking, settings, backup restore, import and UI paths, including TrackingService.kt, SettingsRepository.kt, BackupManager.kt and SettingsViewModel.kt.

Best-effort handling is reasonable for optional audio or haptics, but persistence, restore and state transitions must log structured failures and surface user-visible errors where appropriate.

16. Live GPS coordinates are not explicitly validated

Location: FusedLocationSource.kt:60-74, TrackingService.kt:270-278

Accuracy is checked, but latitude, longitude, finite values, timestamp plausibility and elapsed-realtime validity are not explicitly checked before entering the engine.

Recommendation: Add a shared LocationValidator used by all ingestion paths.

17. Ride recovery may differ from live results

Location: TrackingRepositoryImpl.kt:75-110

Recovery replays stored points but does not preserve all runtime calculator state, such as pending start confirmation, pause state history, max-speed confirmation state and the original timestamp basis.

Recommendation: Persist periodic calculator checkpoints or enough metadata to make replay deterministic.

18. RideCalculator assumes valid coordinates

Location: shared/src/commonMain/kotlin/com/abrar/motolog/shared/domain/engine/RideCalculator.kt:147-150

The shared engine directly calculates Haversine distance. Because it is reusable across Android, iOS and import flows, it should reject invalid coordinates itself rather than relying only on callers.

19. GPX point limit is global rather than per-track

Location: GpxImporter.kt:67, 146-163

A large first track can consume the whole 100,000-point budget and truncate later tracks. The warning does not identify which track was truncated.

Recommendation: Enforce per-track and total-file limits and report omitted points per track.

20. GPX files without timestamps receive 1970 timestamps

Location: GpxImporter.kt:154

timestampEpochMs = ptTimeMs ?: (currentPoints.size * 1000L)

These synthetic values are later used as ride start and end times. Timestamp-less imports can therefore appear as rides from January 1970 and sort incorrectly.

Recommendation: Use a separate relative-time representation or assign an import-time anchor while marking timestamps as synthetic.

21. Imported tracks are not normalized

The parser does not sort timestamps, reject duplicate timestamps, warn about backward time, or split non-monotonic segments. The calculator may reject points while the database still stores the original invalid sequence.

Recommendation: Normalize and validate the entire track before calculating or saving it.

22. Backup archives have no integrity checksum

Location: BackupManager.kt:36-46, 96-160

The manifest contains counts but no per-entry hash, archive checksum or authentication. Corrupted or manually edited archives can be partially accepted.

Recommendation: Add per-entry SHA-256, byte lengths, required-entry declarations and optional authenticated encryption for sensitive location backups.

23. Backups omit mileage cycles and persisted settings

Locations: app/src/main/java/com/abrar/motolog/data/io/BackupManager.kt:37-61, 100-159, 248-260 and app/src/main/java/com/abrar/motolog/data/local/MotoLogDatabase.kt:28-38

The database contains mileage-cycle records, but BackupManager does not inject a mileage-cycle DAO and does not serialize or restore that table. The backup settings model also omits persisted values such as voice announcements, thermal eco mode, disclaimer acceptance, battery-guidance state and dashboard colors.

Impact: A backup advertised as complete silently loses mileage history and preferences.

Recommendation: Add every persisted entity and setting to a versioned backup format. Add round-trip tests that compare all tables and preferences before and after restore.

24. Calculator state is accessed concurrently without confinement

Locations: app/src/main/java/com/abrar/motolog/service/TrackingService.kt:73-94, 185-321, 407-466, 630-650 and shared/src/commonMain/kotlin/com/abrar/motolog/shared/domain/engine/RideCalculator.kt:35-47

Location collection mutates the non-thread-safe RideCalculator from one coroutine while pause/resume commands, stop, checkpointing and statistics reads can occur from other coroutines or threads.

Impact: Race-dependent statistics, lost pause commands, inconsistent snapshots and nondeterministic ride state.

Recommendation: Confine all calculator access to one coroutine/actor or protect it with a mutex. Apply the same rule to AutoPauseStateMachine and SpeedAlertEngine.

25. Rejected GPS samples are persisted as valid route points

Location: app/src/main/java/com/abrar/motolog/service/TrackingService.kt:267-321

When RideCalculator.process() returns Rejected, the service substitutes a zero-speed state but still creates and sends a RidePointEntity with isGap = false.

Impact: Maps and GPX/CSV exports can contain rejected teleportation, timestamp, acceleration or poor-accuracy samples even though summary statistics excluded them. Recovery may replay those samples and produce different results.

Recommendation: Do not persist rejected points, or add an explicit rejected flag and exclude rejected samples consistently from maps, exports, recovery, elevation and graph calculations.

26. Manual pause is automatically cancelled by the next GPS fix

Location: shared/src/commonMain/kotlin/com/abrar/motolog/shared/domain/engine/RideCalculator.kt:185-192

Any ordinary point with isPaused == false calls manualResume() when the state is MANUALLY_PAUSED. Live GpsPoint instances are created without an explicit paused flag, so the next fix can cancel a user-requested pause.

Impact: Manual pause may last only until the next GPS update; distance and time can be recorded while the rider believes tracking is paused.

Recommendation: Separate explicit pause/resume commands from per-point pause metadata. Manual pause must remain active until an explicit resume action.

27. GPS gaps can immediately trigger auto-pause

Locations: shared/src/commonMain/kotlin/com/abrar/motolog/shared/domain/engine/RideCalculator.kt:152-192 and AutoPauseStateMachine.kt:40-57

A point after a long signal gap is passed to the auto-pause state machine with its later timestamp. The low-speed timer before the blackout can therefore be treated as continuous across the gap.

Impact: A ride can become auto-paused immediately after GPS recovery even though no verified stationary period occurred.

Recommendation: Reset or suspend the low-speed timer across gaps and add a regression test.

28. Duplicate-coordinate route can make RDP downsampling non-terminating

Location: shared/src/commonMain/kotlin/com/abrar/motolog/shared/domain/engine/RouteDownsampler.kt:130-151

For identical coordinates, perpendicular distance remains zero and the selected index can remain equal to the start index. If the algorithm pushes the same interval back onto its stack, it can loop indefinitely.

Impact: CPU exhaustion, UI freeze or ANR while preparing a stationary or duplicate-point route.

Recommendation: Recurse only when maxIndex > start && maxIndex < end. Treat degenerate intervals as terminal and add duplicate-coordinate tests.

29. Route downsampler can violate maxPoints

Location: shared/src/commonMain/kotlin/com/abrar/motolog/shared/domain/engine/RouteDownsampler.kt:49-109

Protected points are always retained, but the code does not handle the case where protected points alone exceed maxPoints. The retry loop can terminate while returning an oversized route.

Impact: Memory and rendering limits are not guaranteed on routes with many gap or pause boundaries.

Recommendation: Define a prioritization policy for protected points or explicitly report that the requested limit is impossible.

30. Non-finite GPS values can corrupt statistics

Location: shared/src/commonMain/kotlin/com/abrar/motolog/shared/domain/engine/RideCalculator.kt:104-109, 147-181

The engine does not reject non-finite accuracy, coordinate, speed or altitude values, and does not enforce geographic ranges. NaN can bypass ordinary comparisons and propagate through Haversine distance, speed checks and totals.

Recommendation: Reject non-finite values and enforce latitude [-90, 90], longitude [-180, 180], non-negative accuracy and non-negative speed where applicable.

31. Start confirmation can cross a GPS gap

Location: shared/src/commonMain/kotlin/com/abrar/motolog/shared/domain/engine/RideCalculator.kt:224-241

Start confirmation uses origin-to-current displacement even when the current point follows a signal gap. A large displacement after a blackout can confirm a ride even though no distance across the gap was credited.

Recommendation: Do not use gap or paused points for confirmation, or reset the confirmation origin after a gap.

32. Release artifact is optionally unsigned

Location: app/build.gradle.kts:32-73

Release signing is applied only when a local keystore exists. The available release artifact is an unsigned APK and no signed app bundle is produced. This allows a release build to succeed while producing an artifact that cannot be uploaded to Google Play.

Recommendation: Make publish tasks fail closed when signing is unavailable. Configure CI signing secrets, build bundleRelease, and verify signatures, versioning, alignment and artifact checksums.

33. Notification actions are functionally ignored

Locations: app/src/main/java/com/abrar/motolog/service/RideNotificationManager.kt:111-126, MaintenanceNotificationManager.kt:130-138 and MainActivity.kt:27-37

Notifications put stop and bike-navigation extras into intents, but MainActivity does not consume them in onCreate() or onNewIntent().

Impact: “Stop (In-App)” can open the default screen without stopping the ride, and maintenance notifications may not navigate to the selected bike.

Recommendation: Handle extras in both activity entry points and dispatch the requested action or navigation destination.

34. Notification permission retry can show the wrong denial dialog

Location: app/src/main/java/com/abrar/motolog/ui/live/LiveScreen.kt:188-215, 543-554

When location permission is already granted and only notification permission is requested, the callback checks missing location keys in the returned permission map. The code can incorrectly conclude that location permission was denied and show the wrong permanent-denial dialog.

Recommendation: Check current permissions using checkSelfPermission() and use a separate notification-only result path.

Build and maintenance findings

23. Target SDK is behind the latest platform level

Location: app/build.gradle.kts:21

The application targets SDK 36 while compiling with SDK 37. Lint reports an old-target warning. This is not currently a build failure, but it can affect platform compatibility, Play Store requirements, foreground-service behavior and permission semantics.

Recommendation: Update the target SDK when the toolchain supports it and test on current Android versions.

24. Dependency versions need scheduled review

Lint identifies newer versions for Kotlin, Android Gradle Plugin, DataStore, Navigation Compose, AndroidX, WorkManager, Play Services Location, MapLibre, kotlinx-datetime, serialization, coroutines and testing libraries.

These are not automatically defects. Use staged dependency updates, run the full suite and verify MapLibre native ABI compatibility after upgrades.

25. Deprecated Compose TabRow API

Location: app/src/main/java/com/abrar/motolog/ui/garage/detail/BikeDetailScreen.kt:173

The current Compose version recommends PrimaryTabRow or SecondaryTabRow. Migrate and add UI tests for selection and accessibility semantics.

26. Compose modifier-order warnings

Lint reports modifier-parameter ordering issues in BikeDetailScreen.kt, CockpitSharedComponents.kt, HistoryScreen.kt, RacingTftDashboard.kt, RetroLiveMap.kt and RouteMap.kt.

Fixing these improves consistency and reduces future lint noise.

27. Locale is cached statically

Location: app/src/main/java/com/abrar/motolog/ui/util/FormatUtils.kt:13-14

Lint reports that caching Locale.getDefault() in a static final field will not react to an in-process locale change.

Recommendation: Resolve the locale when formatting or use a configuration-aware formatter.

28. Missing monochrome launcher icons

Location: app/src/main/res/mipmap-anydpi-v26/ic_launcher.xml and ic_launcher_round.xml

Add monochrome adaptive icon layers for Android themed icons.

29. Unused drawable resources

Lint identifies unused launcher-related drawable resources. Remove them or connect them to the intended icon/theme selection flow.

30. Privacy-policy and network declarations need alignment

The application documentation describes zero cloud tracking and device-only location storage, but the map implementation uses network-backed map styles/tiles. The project documentation also contains placeholder or potentially incorrect external URLs.

Recommendation: Document all network endpoints and data flows accurately, verify that map requests do not transmit precise ride history, replace placeholder URLs before release, and align the privacy policy, Play Console declarations and in-app disclosures with actual runtime behavior.

Recommended remediation order

Phase 1 - Protect user data and safety

  1. Fix device-transfer backup rules.
  2. Validate backups completely before deleting data.
  3. Make GPX import transactional.
  4. Add bounded ZIP streaming and integrity validation.
  5. Validate GPX and live GPS coordinates.
  6. Fix start/stop service race conditions.

Phase 2 - Prevent tracking data loss

  1. Replace the unlimited point channel with bounded backpressure.
  2. Add retry and error-state handling to the batch writer.
  3. Flush or checkpoint on shutdown.
  4. Implement the intended service restart/recovery behavior.
  5. Persist monotonic timestamps for deterministic recovery.
  6. Add an interrupted/recoverable ride state.

Phase 3 - Improve correctness and observability

  1. Fix GPS-loss handling for poor-quality callbacks.
  2. Remove silent exception swallowing around restore and persistence.
  3. Add structured logging and user-visible failure states.
  4. Normalize GPX timestamps and point ordering.
  5. Add lifecycle, import, backup and device tests.

Phase 4 - Maintenance and polish

  1. Update deprecated Compose APIs.
  2. Fix locale caching.
  3. Add monochrome launcher icons.
  4. Remove unused resources.
  5. Review dependency and target SDK updates.
  6. Run iOS shared-module tests in macOS CI.

Final assessment

MotoLog is structurally promising and has a good foundation in its shared calculation engine. It is not yet production-ready for a data-sensitive tracking application because the service lifecycle, persistence failure paths, backup restore path and import validation are not sufficiently defensive.

Addressing Phase 1 and Phase 2 should be considered mandatory before release. Phase 3 is required for reliable diagnostics and support, while Phase 4 improves long-term maintainability and platform compatibility.

Performance improvement plan

The app can be made significantly faster and more battery-efficient. The highest-impact areas are GPS processing, database writes, map rendering, Compose recomposition and large import/export operations.

1. Fix and optimize the GPS persistence pipeline

  • Replace the unbounded Channel.UNLIMITED point queue with a bounded queue and explicit backpressure behavior.
  • Use one dedicated database-writer coroutine and controlled Room batches, typically 50-200 points depending on device testing.
  • Retry transient database failures with bounded exponential backoff and surface persistent failures to the notification/UI.
  • Do not persist rejected GPS samples; they increase database size and route-rendering work without contributing valid statistics.
  • Measure write latency and queue depth during long rides.

2. Use adaptive GPS sampling

Requesting high-accuracy, one-second updates continuously consumes battery and creates unnecessary processing while stationary.

  • Moving: approximately one-second updates.
  • Slow or stationary: three-to-five-second updates.
  • Auto-paused: reduce the update rate while preserving reliable resume detection.
  • GPS lost: progressively back off and restore the normal interval after a valid fix.
  • Expose battery-saver tracking mode and verify its accuracy against representative rides.

3. Confine tracking state to one coroutine

Move RideCalculator, pause state, speed alerts and mutable tracking statistics onto one actor/event loop, or protect them with a mutex. This avoids race conditions and reduces synchronization overhead from multiple concurrent callers.

Commands such as start, pause, resume, stop and location updates should be processed sequentially. Checkpoint and notification code should read immutable snapshots rather than touching mutable calculator state concurrently.

4. Optimize MapLibre rendering

  • Downsample route geometry before passing it to MapLibre.
  • Cache route geometry and elevation data.
  • Do not rebuild the complete route on every GPS update.
  • Update only the current-location marker during active tracking.
  • Re-render route geometry only after a meaningful distance threshold, such as 25-100 meters, or after a time interval.
  • Avoid reloading the full map style when only telemetry visibility or theme state changes.
  • Guard the downsampler against duplicate coordinates and enforce its maximum-point contract.

5. Reduce Compose recompositions

  • Split large cockpit/dashboard composables into smaller stable components.
  • Use immutable UI state models and stable collections.
  • Keep rapidly changing telemetry separate from static cockpit configuration.
  • Use remember for expensive calculations, paths, formatters and derived values.
  • Avoid creating lists, lambdas and formatters inside frequently recomposed dashboard functions.
  • Do not collect unrelated settings in the live screen when only one setting is needed.

6. Optimize history and ride-detail screens

  • Load route points only when the detail screen needs them.
  • Use SQL-side filtering, pagination or downsampling instead of loading every point immediately.
  • Cache prepared route and graph data for repeated screen visits.
  • Run elevation and route preparation on Dispatchers.Default or Dispatchers.IO, never on the main thread.
  • Render a simplified preview first, then refine it asynchronously.

7. Stream backup and import/export operations

  • Do not load every database table into memory at once for backup.
  • Stream large point collections in chunks.
  • Use bounded ZIP reads rather than unrestricted readBytes().
  • Move GPX/CSV/backup processing off the UI scope.
  • Show progress and provide cancellation for large operations.
  • Measure peak heap usage with large GPX files and high-mileage databases.

8. Optimize notifications and formatting

  • Keep notification throttling, but update only when displayed values actually change.
  • Cache date, number and unit formatters rather than rebuilding them for every GPS update.
  • Avoid repeated string construction for unchanged notification sections.
  • Ensure locale changes invalidate formatter caches correctly.

9. Reduce startup time and application size

  • Remove unused drawable resources.
  • Review MapLibre native libraries and ABI filters.
  • Verify that release R8/resource shrinking is effective.
  • Use baseline profiles for startup, live-screen rendering and navigation.
  • Delay initialization of map, voice, sensor and nonessential garage components until needed.
  • Measure cold start, warm start and first-frame time on representative devices.
